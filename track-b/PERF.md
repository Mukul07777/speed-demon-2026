# Track B: performance log

## Where it ended

Best board run: `run-b9a388fc542a`, the code in `src` (commit 4eeb9d1, the SIMD left-pack; first board run `run-8e9b84007bcc`, 89.8 ms, 78.90). T 89.7 ms, M 43.0 MB, S 1073, 78.91 points. From the first Rust version: 208 ms to 89.7, 137.1 MB to 43.0, 64.93 to 78.91 points.

Three lessons:

1. Laptop gains often failed on the box. A 26 MiB peak, answers spread through the next scan, a read-ahead prefetch, a pre-fault, a trailing-OR shortcut, PGO and an exact short-key table all looked fine or neutral on the laptop and tied or lost on the board. The wins that held (no `MADV_POPULATE_READ`, THP off, the futex barrier, the transpose) were the ones whose cause was measured on the box first.
2. Read the score formula. M is capped at 50 for this track, which is 44 MB, so the 28 MB build (`run-004a611bfcd9`, 77.15) earned nothing for its memory and lost on time. Lines cost points too: 1356 down to 1004 was worth more than several speed ideas.
3. Count before building. A stage floor (read 6.3, tokenise 8.9, hash 14.2, lookup about 25 ms of a 42 ms scan) and token counts (79% of tokens are query terms) ruled out most redesigns on paper; the one built anyway (exact 8-byte keys) went from 73.7 to 82.3 ms best.

Key ideas, in order of what they were worth:

- Only query terms are indexed, at document level, with no positions. A token is one AES hash and one cache-line bucket probe, hashed a batch ahead and prefetched 20 tokens ahead, with no branch on hit or miss.
- Phrases are checked during the scan from their rarest word (the anchor) and become pseudo-terms, so a phrase query is a one-term lookup and no document is read twice.
- The corpus is processed in 5 phases of 50 MiB: rows become 16-bit postings and the queries are answered into running tallies per phase, so the index never exists whole (63 MiB to 33).
- The answers of phase k-1 run on threads that have run out of scan claims in phase k, so the scan's barrier tail is used.
- THP disabled from the start except for the term table: the box runs THP `always`, which had charged 2 MiB pages to every half-used region (87 MB to 67 MB on the box).

## Futex barrier (2026-11-01)

Profile with per-thread timestamps showed the pre-scan time was mostly `std::sync::Barrier` wake latency (threads released 1-4 ms after the last arrival), not work. Replaced it with a counter + round word: the last arriver does `FUTEX_WAKE`, waiters spin 3000 pauses then `FUTEX_WAIT`. Medians, 30 rounds, run twice in swapped order: 12 CPUs 80.5 -> 75.6 and 79.8 -> 74.2 ms; cpuset 0-5 97.7 -> 95.7 and 98.0 -> 96.2 ms. S +35.

**Failed:** no spin (80.0 -> 79.2, too small); spin 30000 (worse than 3000 on 12 CPUs, no better on cpuset).

Box verdict on the futex barrier: 98daaff 103.0 ms (run ID not recorded) and 12a83cd 101.5 ms (`run-f645d9256ed9`, 42.3 MB, S 1091, 77.51) against 103.5 ms (`run-798a2a9dd634`, S 1056, 77.41) without it. Small gain over two runs, kept.

## Heavy bitmaps by 64-document transpose (2026-11-01)

The lookup loop now stores only each token's heavy bitmap index. Each document's heavy terms are ORed into a row of bits that stays in L1, and every 64 documents a 64x64 bit transpose moves the rows into the phase's bitmaps. Removing the pass entirely (timing probe) showed a 7% ceiling. Counts rejected two other ideas: skipping non-query tokens (79% of tokens are query terms) and a direct table for 1-3 character tokens (1-2% ceiling). Paired 30 rounds, median ms: 12 CPUs 81.1->78.5 and 76.2->72.2, cpuset 0-5 97.1->91.1 and 98.1->93.0. Peak unchanged, S +54. Box run: `run-3296c9e23550`, 94.0 ms, 43.2 MB, S 1145, 78.18, against `run-f645d9256ed9` 101.5 ms, 77.51 before it (laptop -3 to -6%, box about -7%). Kept.
