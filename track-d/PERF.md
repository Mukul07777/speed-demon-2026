# Track D: performance log

## Where it ended

Best board run: `run-5c222b763b05`, commit c4fe3d7 (the code in `src`). T 119.0 ms, M 67.8 MB, S 608, 72.22 points. From the first Rust version: 166.7 ms to 119.0, 147.1 MB to 67.8, 64.84 to 72.22 points. D's board time swings about 10% between rounds, so this is the best of several samples; the first sample of the same code read 71.84.

Three lessons:

1. Profile first. The expected cost was the search; the profile showed that building the graph took 124 of 190 ms, and prefetched cell growth and a fused rewrite did far more than any search tweak (a binary heap was 17 to 54% slower, a bucket queue changed nothing measurable at first).
2. Laptop gains often failed on the box. The `raptorlake` flags gave about -17% on the laptop and nothing on the box (`run-581623ca9668`), dropping `MADV_POPULATE_READ` lost on the box (`run-9af7b0c83008`, 148.1 ms against 137.9), and the fused growth (-15% on the laptop) came through on the box only as a tie on its first run.
3. Weigh every term of the score. Serving the backward search from the forward graph saved 9 MB (58.8 against 67.8) but cost lines and time, and tied on points (72.16 against 72.22), so it was reverted. Memory, time and lines trade against each other; only the board total counts.

Key ideas, in order of what they were worth:

- Node ids are a random relabelling of a road map, so most of the work is undoing that: cells of 1024 nodes are grown by breadth-first search and renumbered in cell order, so a search touches nearby memory.
- Every build pass is a chain of random misses, so each one prefetches from its queue (cells) or in batches of 64 (head rewrite); growth copies edges straight into the final forward array, and a node's new label lives in its raw entry, so a claim costs no extra miss.
- 4-byte edges (21-bit head, 11-bit weight; the 3,500 heavier edges in a side table), node entries of `start << 5 | degree`, reverse edges filled from atomic in-degree counts with no rows.
- Bidirectional Dijkstra on a circular exact-distance bucket queue, distances in 64-node blocks handed out on first touch, edges prefetched on each new label.
- Memory: queue item free list, u8 in-degrees, u32 distances, `PR_SET_THP_DISABLE`, raw graph and rows released as soon as used.

How to read the table: each row is one step, in order. Run ID, T, M and points are from the live board when a push measured that step; blank means the step was measured on the laptop only (alternating runs, numbers in the text) or the run ID was not recorded. A cell reading `not pushed` means the idea was tried on the laptop only and never sent to the board; `not recorded` means it did run on the board but the run ID was not written down. Failures are marked **Failed** and their code was not kept. D's board times swing by about 10% between rounds on unchanged code (122 to 148 ms), so single runs decide little.

## Backward search on the forward graph (2026-11-01)

Roads are almost all two-way, so the backward graph repeated the forward one. Removed: backward arrays, in-degrees, scatter loop. A u16 `rev` array parallel to `forward.edges` holds the weight of the arc back, filled by a pull pass; one-way arcs go to a sorted list, flagged on the node. Distance blocks are u16, with larger labels in the `wide` map. Laptop peak 65->55 MiB (the grow phase now sets the floor at about 56), best +2%, median -3%. Hash, worked example and six generated seeds match. Box runs: 123.1 ms and 124.0 ms (run IDs not recorded), below.

**Not kept (2026-11-01): the backward search above.** Box 123.1 and 124.0 ms, 58.8 and 58.4 MB, S 669, 72.16 and 72.10, a tie with 119.0 ms, 67.8 MB, S 608, 72.22. Memory gained 0.65, lines and time took it back. Code at 842c452 and tools/wt_d8/v/rev2.rs.

**Not kept (2026-11-02): the backward search with one sorted extras list, S 646.** Box `run-f264faf57075` 125.0 ms, 58.7 MB, 72.11 and `run-df9b23393d48` 128.4 ms, 58.7 MB, 71.82, against 72.24 best. Faster on the laptop (median 114 against 120), slower on the box. Do not retry.
